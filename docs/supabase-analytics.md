# Supabase analytics and sync

Supabase is the single source of truth. The backend reads `master_transactions` through the server-only `SUPABASE_URL` and `SUPABASE_SECRET_KEY`; the browser never receives the secret. Reads are paginated and checked for a consistent total count. A shared in-memory snapshot is refreshed after a successful full sync.

Descriptive Analytics adds its selected category and standardized province to the existing global Analysis Scope on the server. The API filters the shared published-data snapshot before calculating all descriptive aggregates, and caches the result by snapshot and filter combination. Filter changes do not issue Supabase writes or affect predictive or prescriptive requests.

Revenue uses **Deal Price × Quantity − allocated seller-funded order voucher**, before deducting the verified returned-unit share in analytics. Deal Price already incorporates line-level seller price discounts: these must not be subtracted twice. Order-level seller vouchers are allocated proportionally once per order. Shipping, platform fees, and platform-funded vouchers are excluded. Other seller-funded discounts (such as bundle/cashback promotions) require reconciliation of whether they are already reflected in Deal Price before they can be deducted; they are not silently guessed. The original Total Buyer Payment is not used as product revenue. Approved returns with missing returned quantity are not assumed to be full returns, and excessive returned quantities block re-preparation. Quantity is net units and orders count distinct nonblank IDs. Analytics includes eligible, nonduplicate rows. Excluding approved returns nets out returned units and associated revenue; returned-only mode includes approved or positively returned lines.

`data_adjustments` explicitly records `no_sales`, `closure`, `data_gap`, or `anomaly` periods. It is the only source for adjusted-period behavior. `exclude_from_training = true` excludes every calendar month touched from forecast training and MoM/YoY comparisons. No threshold is applied, and adjustments never change KPI totals. Missing adjustment tables are treated as no adjustments. See [predictive-analytics.md](predictive-analytics.md) for model and comparison behavior.

The sync order is product and geography mapping upserts, creation of a `running` `etl_runs` row, replacement and insertion of master rows, completion of run counts, superseding previous completed runs, then pruning to the five newest nonrunning runs. Failures after run creation mark that run failed. The ETL log is created before deleting master data so a failed log insert cannot leave the table empty.

For local development, run `npm run server` and `npm run dev`. Vite proxies `/api` to port 4000. The upload and prepared-data paths are ignored by Git because source spreadsheets contain personal information.
